# Roster and routing — fleet policy

Read before the first dispatch; lanes read their role and applicable routing rules.
Installed by game-orchestration; model pins and permissions remain binding.

## Roster

| Role | Who (pinned in `.claude/agents/`) | Does | Never |
|---|---|---|---|
| **Lead / main orchestrator** | **Opus 5.5 (1M)**, high — the session itself (Tether: set the session's Effort row to high; each app repo's `.claude/settings.json` carries `effortLevel: high`, so a session left on Tether's default Effort starts at high; a picked Effort still overrides it, and a lead that finds itself at any other effort says so in its first report) | Plans waves, writes briefs, spawns agents, verifies their work, runs builds/tests/the dev server, captures screens, gates, integrates and pushes, deploys, owns the tracker's STATUS/DONE; may call the **image lane** directly for a single asset and route the result to `design-director` | Implements features; makes design calls (rule 3 has the one exception) |
| **Design: all of it** | `design` (**Opus 5.5 (1M)**, high) | Every piece of design: UI/UX structure and flow, layout and spacing, type scale, colour and tokens, component and screen design, empty/loading/error states, interaction and motion specs, iconography — plus the design spec a piece is judged against. **Every raster asset it needs is generated by the Codex image lane it drives** | Anything that isn't design; grading its own design; product code beyond a design's own spec/tokens/styles; shipping design no one judged |
| **Design director** | `design-director` (**Opus 5.5 (1M)**, high, read-only) | The run's design judge: **APPROVE/REJECT against one reference** (the bar screen, mock or concept the run doc names); a REJECT names **every BLOCKING finding, ranked** — bar line, evidence, smallest change (gauntlet-core › Findings) | Executing, editing, building; being the first opinion where the blind critics exist |
| **Image assets — icons, buttons, illustrations, textures, reference images** | **The Codex image lane (`astra`, High)** — `codex exec -m gpt-6-astra -c model_reasoning_effort=high` running the built-in `imagegen` skill (gpt-image-2 on the subscription, no API key) — **driven by the `design` lane**; the lead may call it directly for a single asset | Every raster asset a design needs: app and UI icons, buttons and controls, illustrations, textures, backgrounds, empty-state art, marketing and social images, and the **reference images** a design brief needs before the design exists | Judging; anything outside the design lane's brief; 3D of any kind; committing an asset without its recipe |
| **Complex coding** | `builder` (**Sonnet 5.5**, medium) | App and API logic, data model and migrations, auth, integrations, build and tooling, the hard refactors | Deploying; grading its own UI; merging |
| **Light coding** | `scout` (**Sonnet 5.5**, medium) | Wiring, config, docs, copy, data entry, recon reported as `file:line` | Redesigns; anything architectural (hands the seam back to `builder`) |
| **The lead's critic** | `wave-check` (**Opus 5.5 (1M)**, medium, read-only for code) | Reviews every wave plan **before** any brief goes out | Proposing or designing work |
| **The lead's advisor** | `advisor` (**Fable 5.2 (1M)**, high, read-only) | Counsel to the lead only: advice on a hard call; **must** be consulted before a third attempt at a twice-failed problem; **decides in the owner's place inside the night protocol** (rule 11) | Building, editing, judging a candidate, dispatching; lifting a hard stop |
| Blind critics / ground-truth audit | workflow agents — **Opus 5.5 (1M)**, medium, named on every `agent()`; never inherited from a Fable lead | Blind replicas per screen against its bar, plus one naive reader per capture | — |

**Never assign work to a retired role name or model.** In this fleet there is no `artist`, no
`astra` **role** (the Codex image lane is a child the `design` lane runs, not a peer agent), no
Fable 5.1 or earlier and no Sonnet 5, and **no 3D pipeline at all**: Meshy, Blender, Unity, rigs, meshes and
textures-for-3D are out of scope for apps — if a task genuinely needs 3D, it belongs to the Games
fleet. The roster table above and `.claude/agents/` frontmatter are the pins; no brief, tracker or
prompt may name a retired role or model. **Fable 5.2 has two uses only: the lead under rule 10 and
the `advisor` pin (rule 11)** — no maker lane, judge or workflow agent runs on it.

## Routing rules

1. **Spawn the repo roster by name with no model/effort override — the one exception is the logged step-up in rule 9.** The global
   `native-orchestration` skill explicitly exempts repo-local rosters from its override rule.
2. **All design work goes to `design`; all image *generation* goes to the Codex image lane.** The
   lane has exactly one job: raster assets — icons, buttons, illustrations, textures, reference
   images. It runs the pinned command `codex exec -m gpt-6-astra -c model_reasoning_effort=high`
   with the built-in `imagegen` skill, **driven by the `design` lane**; the lead may call it
   directly for a single asset and then route the result to `design-director`. No leaf outside the
   design lane runs imagegen. Every generated asset is committed **with its recipe** (the exact
   prompt, the command, the output path), so it can be regenerated or re-commissioned.
   - **One image lane at a time.** The lane spends the owner's subscription quota: no speculative
     batches, no asset the brief did not ask for — ask `design` first whether an existing asset or
     a code-drawn icon (inline SVG, an icon font, a CSS/`currentColor` shape) does the job cheaper.
     A raster asset is for what vector/CSS genuinely cannot do.
   - **Never re-inline a raw generated image into a transcript.** The built-in tool writes to
     `~/.codex/generated_images/<threadId>/` — copy the file out to the lane's paths and reference
     it by path. A multi-MB base64 payload in a codex transcript hits the 16 MiB frame cap and
     makes the session un-resumable.
3. **The lead never implements in a run.** If a run's lead is about to edit code or design, it
   spawns an agent instead. The lead keeps the build/test gates, the shared dev instance, screen
   captures, integration and pushes, deploys, tracker STATUS/DONE, and the lifecycle of any
   long-running process it starts. **Interactive exception:** in a session that is *not* a run, the
   session may make **one small edit itself** when all of these hold — one file, not design, not
   Core/business logic or schema, and no design verdict needed (a typo, a doc line, a config value,
   a one-line fix with its test). Anything bigger, or a second edit, goes to the roster. The edit is
   still verified by someone other than its author when it changes behaviour.
4. **Verdicts come from instruments, not the maker.** A design is judged against **one** reference
   by the blind critics, with `design-director` ruling where they disagree; until the critic
   workflows exist, `design-director` judges alone — and the report says so. A UI claim is verified
   with a **screen capture from a real browser at the run doc's viewports** (desktop and phone),
   never with prose; the run's own gates (tests, typecheck, lint, build) are read from their real
   output line. **Independence is by context, not by model**: maker and director share a model's
   blind spots — reports say "blind, fresh-context", never "independent model", and a verdict that
   rests on taste rather than a reference or a measured number is labelled as such.
5. **Hand-offs:** `scout` → `builder` when a task turns out to be architectural; `design` → the lead
   for a better reference or a re-commission when a piece cannot reach its bar; `builder`/`design`
   → the lead for anything needing a deploy.
6. **Prove runtime identity on the first real dispatch and at wave boundaries.** Record the
   lead and each role's actual provider/model/effort from startup telemetry or native transcript
   metadata; labels/requested models alone are not proof. Use the fleet's `models` helper where
   supported, otherwise record the native evidence and applicable roster/owner-selected model.
   Check identity before expensive work. A separate no-op probe is needed only when the harness
   cannot expose it otherwise, once per runtime configuration change, not per handover. Missing
   telemetry is UNKNOWN; wait for its event rather than sleep-polling. A confirmed mismatch stops
   the affected lane for the owner; never silently substitute a model.
7. **HARD RULE: every Opus agent is Opus 5.5 (`claude-opus-5-5[1m]`), never Opus 5.** Applies to
   pins, spawns and workflow `agent()` calls alike. Do not use the global `~/.claude/agents` for a
   run: this repo's roster is the reviewed policy.
8. **Every agent logs its own work** in this repo's tracker/write protocol (beads — see Tracking) —
   as a **one-line row**: state, verdict, and the path to the body. The body goes in your own file;
   never paste it into the tracker (gauntlet-core › *the tracker is an index*). The lead owns STATUS and DONE. `wave-check` and `design-director` are read-only apart from their
   own verdict and log rows — **enforced** for file edits by the fleet gate, the user-level
   PreToolUse hook `~/bin/fleet-gate.py` (static rules; inside a checkout they can write Markdown
   only); their Bash stays open for inspection, and there the rule is still their
   word.
9. **A rejected piece steps up once, in a fixed order (owner 2026-11-15).** The pins are where
   every piece starts; effort rises before the model does.
   - **First REJECT — check the brief, keep the pin.** Did the lane have the context — the plate,
     the named sections, the acceptance line, the triaged finding IDs? If not, the brief failed:
     fix it and re-commission on the same pin.
   - **Second REJECT on a complete brief — one step up, for that piece only.** Pass `effort` one
     level above the pin on that one spawn (`medium` → `high`, `high` → `xhigh`). A Sonnet role
     already pinned at `high` does not go to `xhigh`: spawn it with `model: opus` (Opus 5.5,
     rule 7) at `medium` instead. Consult `advisor` first (rule 11): the stepped-up attempt
     follows its advice.
   - **Third REJECT — park**, as before; the park card carries the advisor's advice and says
     whether a model move is the recommendation, and the owner decides it.
   Log it before the spawn, in the bead and the brief: `STEP-UP <piece> <role> <from> -> <to>
   after REJECT 2 (<verdict path>)`. Rule 6 reads the logged value as the expected one for that
   spawn; a difference from the pin with no STEP-UP line is a mismatch. Never a step down, never
   two steps, never on a first attempt, never for a judge (`wave-check`, `design-director`, the
   critics) — a judge's effort changes only by owner ruling. Every wave report lists its
   step-ups and how each ended.
10. **Fable 5.2 lead — the lead may decide to move itself up, on written criteria (owner
    2026-11-15).** Every run starts on Opus 5.5 at high. Fable 5.2 (`claude-fable-5-2[1m]`,
    effort high) runs only as this lead or as the `advisor` pin (rule 11): never a maker lane, a
    judge or a workflow agent. It uses the plan's limits about twice as fast as Opus 5.5, so the
    bar is high.
    **All four must hold:**
    - **(a) A gauntlet run at a clean boundary** — run start, a wave boundary or a handover; no
      lane in flight, nothing half-integrated or unpushed. Never an interactive session, never
      mid-wave.
    - **(b) Limits allow it** — on the session's account the weekly limit is at most 50% used and
      the 5-hour window at most 50% used, read live. A reading older than one hour is UNKNOWN,
      and UNKNOWN means no move.
    - **(c) One Fable lead per account** — no other live session on that account is on Fable 5.2.
      An `advisor` call is not a session.
    - **(d) The lead is already at high.** Effort rises before the model (rule 9's order).
    **And at least one of:**
    - **Scale** — the plan `wave-check` passed for the next wave has 8 or more pieces, or 4 or
      more lanes in flight at once, and the run is expected to outlast one lead context (a
      handover is planned or has already happened).
    - **Stall with full context** — in the current wave, two lead-attributable misses: a wave plan
      `wave-check` REJECTed twice, or two pieces parked at their third REJECT where triage puts
      the cause in the plan or the brief rather than the lane. The lead had the context, tried,
      and still got it wrong.
    - **An open technical problem that stays open** — a root-cause or architecture question
      spanning the data/backend layer and at least two other subsystems, on which two scoped
      investigations came back INCONCLUSIVE or contradicted each other.
    **Record it before acting** — `~/gauntlet/<run>/fable/<YYYY-MM-DD>.md`: the criteria met, the
    evidence paths, the limit reading with its timestamp, and the one line that would overturn
    it. No record, no move. At night the move is `advisor`'s decision like any other (rule 11).
    **How the move happens.** The successor starts on Fable 5.2 at the boundary. Today Tether
    applies a successor's model only from the owner's handover request — the `handover` tool
    keeps the predecessor's model — so the lead writes the record, puts a `FABLE-READY` card at
    the top of its next report and **keeps working on Opus 5.5** until the owner hands it over
    with Fable 5.2 selected. It never waits idle for the switch.
    **While on Fable 5.2:** lanes keep their pins; workflow critics name Opus 5.5 on every
    `agent()` (a critic that would inherit Fable does not run); rule 6 records the lead's real
    model id — a Fable lead never reports itself as Opus; the wave report shows lead usage under
    Fable separately.
    **Stepping back down:** at the next wave boundary once none of the three triggers holds; and
    at the next clean point, without waiting for the boundary, when the weekly limit passes 75%
    used. The record gets the step-down line. The numbers here (8 pieces, 4 lanes, 50%, 75%) are
    starting values, measured at the first wave end that used them.
11. **`advisor` — Fable 5.2 at high: the lead's counsel and the night decider (owner 2026-11-21).**
    Only the lead calls it; a lane that needs advice hands back under its brief's *Return when*.
    It is fresh-context and read-only: it never builds, edits, judges a candidate or dispatches,
    and it replaces no instrument — `wave-check`, the critics and `design-director` still rule on
    plans and pieces.
    - **May, at any hour:** a hard call (a plan, a trade-off, a diagnosis) where a stronger second
      read is worth its cost. By day the answer is advice: the lead decides and the owner still
      rules at checkpoints.
    - **Must, by day — a problem two attempts did not solve.** Before a third attempt at the same
      problem — a piece at its second counted REJECT on a complete brief (with rule 9's step-up),
      or a fault, gate or bug the lead or its lanes have twice failed to fix — the lead consults
      `advisor`, and the next attempt follows its advice. If that attempt fails too, the problem
      goes to the owner with what was tried and the advice given: a piece by its third-REJECT
      card, anything else as a question card. No further attempt meanwhile; other work continues.
    - **Must, at night — every decision.** Inside the night protocol (`orchestration.md` › Night
      protocol) the lead takes each open question to `advisor`, which decides in the owner's
      place. The lead never answers one itself, and `advisor` cannot lift a hard stop.
    **The brief is one question:** the mode (ADVICE, STUCK or NIGHT RULING), the options, the
    documented recommendation if there is one, the evidence paths and exact sections, what was
    tried, and what would be irreversible. **The answer is a receipt:** the ruling or advice, the
    reasons, and the one line that would overturn it. Log every call where the work is tracked:
    `ADVISOR <mode> <question> -> <answer path>` (at night, in the night log). Fable 5.2 uses the
    plan's limits about twice as fast as Opus 5.5: one question per call, never a standing lane.
    Rule 6 proves it ran on `claude-fable-5-2`; on a mismatch or a failed spawn the answer does
    not count — by day ask the owner, at night the question waits as a morning-report card.
    Under a Codex lead the duty goes to a fresh Codex agent on the owner's model at high
    reasoning effort; the Fable pin does not apply (`orchestration.md` › A Codex lead).
12. **A behavioural hunt is one `scout` lane, optional per piece, web UI only (owner 2026-11-22).**
    For a DOM-app piece whose flow no lane in the wave exercises, the lead may brief one `scout` to
    run stillhunter (`~/tools/stillhunter`, runner at `dist/hunt.mjs`) against a disposable
    instance, as `gauntlet-core.md` › Behavioural hunt defines it. It is a maker-side instrument,
    not a judge: its output enters the ledger only through the lead's triage, in the BLOCKING/NOTE
    triad, and only findings reproduced twice are eligible. It replaces no gate, no `wave-check`
    pass and no `design-director` verdict, and it never runs against the shared dev instance or
    production.
