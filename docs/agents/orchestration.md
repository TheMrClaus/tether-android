# Orchestration policy — binding for every session in this repo

This is the default working mode for **any** session in **any** app repo of the fleet — not a
global Claude/Codex setting: each repo carries its own tracked copy, so a session started anywhere
in the repo (lead, leaf, interactive, spawned child) reads it. Canonical text and the installer:
`~/bin/game-orchestration --fleet app` (`install --fleet app --all` to re-apply, `verify --fleet
app --all` for drift). What a run is — the bar, waves and the standing brief rules — is in
`docs/agents/gauntlet-core.md`.

**One line:** the session you start here is a **lead that orchestrates**; work goes to a named
repo-local agent with a pinned model+effort, and **no piece is judged by the agent that made it**.
A run's lead never builds; an interactive session may make one small edit itself (rule 3).

## Roster

| Role | Who (pinned in `.claude/agents/`) | Does | Never |
|---|---|---|---|
| **Lead / main orchestrator** | **Opus 5.5 (1M)**, high — the session itself | Plans waves, writes briefs, spawns agents, verifies their work, runs builds/tests/the dev server, captures screens, gates, integrates and pushes, deploys, owns the tracker's STATUS/DONE; may call the **image lane** directly for a single asset and route the result to `design-director` | Implements features; makes design calls (rule 3 has the one exception) |
| **Design: all of it** | `design` (**Opus 5.5 (1M)**, xhigh) | Every piece of design: UI/UX structure and flow, layout and spacing, type scale, colour and tokens, component and screen design, empty/loading/error states, interaction and motion specs, iconography — plus the design spec a piece is judged against. **Every raster asset it needs is generated by the Codex image lane it drives** | Anything that isn't design; grading its own design; product code beyond a design's own spec/tokens/styles; shipping design no one judged |
| **Design director** | `design-director` (**Opus 5.5 (1M)**, high, read-only) | The run's design judge: **APPROVE/REJECT against one reference** (the bar screen, mock or concept the run doc names), naming the **single biggest gap** | Executing, editing, building; being the first opinion where the blind critics exist |
| **Image assets — icons, buttons, illustrations, textures, reference images** | **The Codex image lane (`astra`, High)** — `codex exec -m gpt-6-astra -c model_reasoning_effort=high` running the built-in `imagegen` skill (gpt-image-2 on the subscription, no API key) — **driven by the `design` lane**; the lead may call it directly for a single asset | Every raster asset a design needs: app and UI icons, buttons and controls, illustrations, textures, backgrounds, empty-state art, marketing and social images, and the **reference images** a design brief needs before the design exists | Judging; anything outside the design lane's brief; 3D of any kind; committing an asset without its recipe |
| **Complex coding** | `builder` (**Sonnet 5.5**, high) | App and API logic, data model and migrations, auth, integrations, build and tooling, the hard refactors | Deploying; grading its own UI; merging |
| **Light coding** | `scout` (**Sonnet 5.5**, medium) | Wiring, config, docs, copy, data entry, recon reported as `file:line` | Redesigns; anything architectural (hands the seam back to `builder`) |
| **The lead's critic** | `wave-check` (**Opus 5.5 (1M)**, medium, read-only for code) | Reviews every wave plan **before** any brief goes out | Proposing or designing work |
| Blind critics / ground-truth audit | workflow agents (inherit the lead: Opus 5.5) | Blind replicas per screen against its bar, plus one naive reader per capture | — |

**Never assign work to a retired role name or model.** In this fleet there is no `artist`, no
`astra` **role** (the Codex image lane is a child the `design` lane runs, not a peer agent), no
Fable and no Sonnet 5, and **no 3D pipeline at all**: Meshy, Blender, Unity, rigs, meshes and
textures-for-3D are out of scope for apps — if a task genuinely needs 3D, it belongs to the Games
fleet. The roster table above and `.claude/agents/` frontmatter are the pins; no brief, tracker or
prompt may name a retired role or model.

## Routing rules

1. **Spawn the repo roster by name with no model/effort override.** The global
   `native-orchestration` skill explicitly exempts repo-local rosters from its override rule.
2. **All design work goes to `design`; all image *generation* goes to the Codex image lane.** The
   lane has exactly one job: raster assets — icons, buttons, illustrations, textures, reference
   images. It runs the pinned command `codex exec -m gpt-6-astra -c model_reasoning_effort=high`
   with the built-in `imagegen` skill, **driven by the `design` lane**; the lead may call it
   directly for a single asset and then route the result to `design-director`. No leaf outside the
   design lane runs imagegen. Every generated asset is committed **with its recipe** (the exact
   prompt, the command, the output path), so it can be regenerated or re-commissioned.
   - **One image lane at a time.** The lane spends the owner's subscription quota: no speculative
     batches, no asset the brief did not ask for — ask `design` first whether an existing asset or
     a code-drawn icon (inline SVG, an icon font, a CSS/`currentColor` shape) does the job cheaper.
     A raster asset is for what vector/CSS genuinely cannot do.
   - **Never re-inline a raw generated image into a transcript.** The built-in tool writes to
     `~/.codex/generated_images/<threadId>/` — copy the file out to the lane's paths and reference
     it by path. A multi-MB base64 payload in a codex transcript hits the 16 MiB frame cap and
     makes the session un-resumable.
3. **The lead never implements in a run.** If a run's lead is about to edit code or design, it
   spawns an agent instead. The lead keeps the build/test gates, the shared dev instance, screen
   captures, integration and pushes, deploys, tracker STATUS/DONE, and the lifecycle of any
   long-running process it starts. **Interactive exception:** in a session that is *not* a run, the
   session may make **one small edit itself** when all of these hold — one file, not design, not
   Core/business logic or schema, and no design verdict needed (a typo, a doc line, a config value,
   a one-line fix with its test). Anything bigger, or a second edit, goes to the roster. The edit is
   still verified by someone other than its author when it changes behaviour.
4. **Verdicts come from instruments, not the maker.** A design is judged against **one** reference
   by the blind critics, with `design-director` ruling where they disagree; until the critic
   workflows exist, `design-director` judges alone — and the report says so. A UI claim is verified
   with a **screen capture from a real browser at the run doc's viewports** (desktop and phone),
   never with prose; the run's own gates (tests, typecheck, lint, build) are read from their real
   output line. **Independence is by context, not by model**: maker and director share a model's
   blind spots — reports say "blind, fresh-context", never "independent model", and a verdict that
   rests on taste rather than a reference or a measured number is labelled as such.
5. **Hand-offs:** `scout` → `builder` when a task turns out to be architectural; `design` → the lead
   for a better reference or a re-commission when a piece cannot reach its bar; `builder`/`design`
   → the lead for anything needing a deploy.
6. **Prove the models — before wave 1 and at every wave boundary.** The lead confirms it runs as
   `claude-opus-5-5[1m]` before wave 1, and every role's first spawn is a no-op probe. At each wave
   end the lead runs `game-orchestration models --fleet app <session-id>` (each spawn's transcript
   model against the pins) and records the line in the wave report. Any mismatch: stop and ask the
   owner.
7. **HARD RULE: every Opus agent is Opus 5.5 (`claude-opus-5-5[1m]`), never Opus 5.** Applies to
   pins, spawns and workflow `agent()` calls alike. Do not use the global `~/.claude/agents` for a
   run: this repo's roster is the reviewed policy.
8. **Every agent logs its own work** in this repo's tracker/write protocol (beads — see Tracking).
   The lead owns STATUS and DONE. `wave-check` and `design-director` are read-only apart from their
   own verdict and log rows — **enforced** for file edits by the fleet gate (inside a checkout they
   can write Markdown only); their Bash stays open for inspection, and there the rule is still their
   word.
9. **Jev advises; instruments and named agents decide.** Use it for triage, evidence filtering and
   the tool-call net. Never as the design critic, never as a verdict, never to choose who does the
   work.

## Cost discipline

Delegation is not automatically cheaper, and the bill is dominated by **steps × context**, not by
agent count. Measured on a real run (~50 agents, ~2h, two sessions): **8 long self-iterating lanes
were ~68% of all tokens** (each ~180-300 steps, each step re-reading a 150-260k context); the lead
~15%; the blind critics + audit + `wave-check` together ~1%. Nothing in that run used more than
~350k of context.

- **Cache reads cost the same on Opus and Sonnet** on this plan, so a model downgrade halves the
  *output* line but does nothing for cache reads — **only shorter trajectories and smaller
  per-step contexts reduce them**.
- On this plan **Opus is offered only with the 1M context** (`default` and `opus[1m]` both resolve
  to `claude-opus-5-5[1m]`): there is no cheaper non-1M Opus to switch to, so never propose "drop
  the `[1m]`". Moving a lane off Opus is the model lever, and it belongs to iterative/mechanical
  lanes only — never to the judging roles.

Rules — binding in every brief:

1. **Iteration budget.** A lane does its work in ONE pass, checks it ONCE, writes its receipt, and
   stops. No lane iterates against its own taste (rule 4: the judges judge). A doubt is recorded as
   a candidate in the receipt; the lead decides.
2. **Receipts, not transcripts.** A lane's answer is a short receipt — facts, paths, evidence, open
   candidates — written to the run-artefacts dir. Never paste raw tool output or long prose back
   into the lead: every lead step re-reads its own context, so what lands there is the run's real
   cost.
3. **Small contexts.** A brief names the exact section a lane must read, never "read docs X in
   full".
4. **Batch the fan-out and reuse.** One `scout` covering three pieces beats three scouts covering
   one each; resuming a lane beats re-spawning it for the same work.
5. **The wave-end models line is also the cost checkpoint** (`gauntlet-core.md` › what a wave is,
   item 5): when a run is over budget, or the owner asks, the wave report carries the per-role
   spend from `game-orchestration cost <session-id>`. A wave whose cost is one role is a policy
   finding, not a mystery.

## Verification discipline (every claim)

- A claim is verified against the artifact, not against the agent's summary. Independent context,
  independent instrument. For anything user-visible that means **a capture from the real app**, not
  a description of the diff.
- **A number entering a brief must be re-derived by someone other than the brief's author.**
- The verifier never edits. The lead decides whether a finding is reproducible, in scope and
  blocking, and never sends the same unchanged candidate back for another verdict.
- Gates are read from their real output line (e.g. `failed` **and** `total`), not from `$?` in a
  pipe. A shrinking total is a red flag.
- **Round limits:** a *review* of one deliverable is one round, plus a re-review only when blocking
  fixes materially change it — **maximum three**. This caps re-reviews, not the build → judge loop:
  a piece that loses to its reference goes back in as a *changed* candidate and is judged fresh,
  for as many passes as the run doc allows.

## Tracking (beads — the machine layer)

Every repo in this fleet carries its own **beads** store (`.beads/`, issue prefix per repo) — the
live state of claims, dependencies and evidence. GitHub issues and the repo's markdown docs stay the
human-facing tracker; beads is where the machine answers "what is claimable right now". `bd` lives
at `~/bin/bd` (symlinked into `/usr/local/bin`) and is **pinned**: never upgrade it mid-run — the
store carries a Dolt schema version and an older binary refuses a newer store.

- **Dispatch from the frontier, never from memory.** `bd ready` is the claimable set (unblocked,
  unclaimed, not deferred); `bd blocked` is what is waiting on someone else. Never hand a leaf work
  that `bd ready` does not offer.
- **Claim before you touch a file:** `bd update <id> --claim` — atomic, so two agents can never hold
  one bead. A lost race exits 13: re-read, do not retry blindly. An abandoned claim (over 2 h) is
  recovered with `bd stale` then `bd update <id> --assignee <you> --force` — never quietly stolen.
- **Every agent logs its own work** (this is the write protocol): checkpoints and evidence go in the
  bead — `bd update <id> --append-notes "done… half… files… next…"`, narrative in
  `bd comment <id> "…"`. A claim with no note is not progress, and `bd history <id>` is the trail.
- **Done is two steps, exactly like a review round:** the worker sets `-s done` with its evidence
  line (`--append-notes "EVIDENCE: gate line, sha, captures, paths"`); a **different** actor
  promotes it to `verified`. Nobody verifies their own bead.
- **A 👤 gate is a bead:** `bd update <id> -s blocked --append-notes "needs owner: …"` and label it
  `human`, so it lands in the owner's inbox (`bd human list`, `bd human respond <id> -r "…"`).
- **Never write a secret into a bead.** Beads is a pushed database: `bd dolt push` syncs issue
  history to the repo's own origin under `refs/dolt/data`.
- **One writer per board.** If a repo still has a markdown tracker as its writer, beads stays a
  read-only snapshot until that tracker hands over — never keep the same rows current in both places.

Setup, seeding and the full command map: `~/wiki/wiki/concepts/beads-tracking.md`.

## Jev (TypeSafe) — advisory decision model

Vendor: TypeSafe's Jev via **OpenRouter** (`typesafe/jev-1.13`, `POST /api/v1/systemone`; the
provider serves a **dated snapshot**, so log `response.model` and treat the date as part of the
version). Two independent implementations, each with its **own question set**: the leaf gate
(`~/bin/jev-gate.py` — a Claude Code + Codex hook) and the orchestrator-side judge
(`plugins/jev-judge`, `pre_tool_call`, shadow). **A question fix must be applied twice.**

- **What it is for:** cheap (≈$0.00002), fast (≈0.35 s) typed answers — triage between waves,
  evidence filtering *before* a critic sees it, a net over destructive/exfiltration-shaped calls.
- **What it is not:** not a design critic (text-only), **not a verdict** (critics, audit and
  `design-director` decide), not routing (the lead routes), not a substitute for reading an
  instrument's own output line. **Its answer is a number, not a citation.**
- **How the gate decides** (`~/.config/jev-gate/config.json`, current mode: **enforce**,
  `auto_allow: false`, `model_asks: false`). The shell text is parsed (quotes, heredocs, `$(…)`,
  `bash -c`, `cd`, variables…), so a commit message or PR body that *mentions* a command is not that
  command. Rules first, model second:
  - **DENY rules block**: force-push/delete of `main`, `rm -r` of `~`, a home or state dir, a repo
    root, `.git` or a system tree, disk/power commands, SQL DROP through a db client.
  - **FLAG rules ask**: the policy's own hard rules (`git add -A`/`.`, `commit -a`, discarding
    uncommitted work in a shared checkout, `stash drop`), secrets paths, `sudo`, `reset --hard`,
    unresolved `rm -r` targets, file edits to secrets/`.git`/harness settings/the gate, and — for
    `wave-check`/`design-director` — any non-Markdown edit in a repo (that one is a DENY).
  - **Jev** judges what the rules leave (Bash only; a file edit shows a path, not intent, so it is
    never sent). A verdict over threshold that no rule backs is a **hunch**: hunches are **written
    down, not asked** (`model_asks: false`) — `jev-gate.py --hunches [days]` lists them for review.
  - **Jev may only make a result stricter, never looser.** It can hold, ask or stop; it can never
    authorise. A Jev "allow" alone never green-lights a side effect, an advance, or a completion.
- **What an `ask` does depends on the harness:** interactive or Tether session → an approval
  prompt/chip, **the turn waits for the owner**; headless `claude -p` with no prompt tool → the call
  is **denied**. A **`bypassPermissions`** session would approve an ask unseen, so there the gate
  **denies** every rule-backed ask instead and says why.
- **Coverage:** Claude Code `PreToolUse` + `PermissionRequest` in `~/.claude/settings.json` and every
  Tether account; Codex `PreToolUse` in `~/.codex/hooks.json`. The role rule rides on the same hook.
- **Health:** `jev-gate.py --health` (errors / fail-opens, last 24 h). A broken gate fails open and
  says so in a `systemMessage`; a command it cannot judge within 3 s is asked, not waved through.
- Never route a secret through it: payloads are capped and key-, JWT-, password- and
  URL-credential-shaped strings are masked, but the question still leaves the box.

## Environment rules

- **The shared dev instance is single-instance: wait, never kill.** Only the lead starts or stops a
  long-running shared process (the deployed dev/preview instance, a seeded local service, a
  database container). A lane may run its own builds and tests — that is why lanes get worktrees.
- **Never point anything at production.** Mutating scripts, migrations and tests run against a
  disposable local/dev target; a deploy is the lead's, and it is **verified against the served
  artifact** (build id/hash plus a real request to the live URL), never against a build log alone.
  A repo's own deploy rules (its `CLAUDE.md` / runbook) win for that repo where they are stricter —
  including any "never touch this service from a lane" rule.
- **UI work is verified in a real browser** (Playwright CLI per the house convention) at the run
  doc's viewports — desktop **and** a phone width — with the capture attached to the evidence.
  "It builds" is not evidence that a screen works.
- **A shipped app must look designed, not default** (owner rule). Design work names its reference
  and its tokens; a piece that looks like a framework's untouched default does not pass its bar.
- **Secrets never touch git, a wiki, a memory file, a session summary or a bead.** New credentials
  are wired into the env/config of the services that need them, files stay `600`, and only
  placeholders go into docs (`.env.example`). Public-repo hygiene: block dotfile/VCS paths at the
  proxy, never let a build copy them into a static bundle.
- **Commit by explicit path; never `git add -A`/`git add .`/`commit -a`; no AI `Co-authored-by`
  trailers.** Never discard uncommitted work in a shared checkout — the tree belongs to every
  workstream in the repo. Push the gated sha explicitly and check `git log origin/main..<sha>` for
  another workstream's unpushed commits before you do.
- **Dependencies: latest stable, not minimal** when a bump is in scope; one bump per PR-shaped change
  with the gate re-run.
- Big binaries, screenshots, generated images and run artefacts stay **outside git**.
- **File upstream bugs** when the root cause is upstream rather than patching around it silently,
  and say in the PR which half is a local workaround.
- 3D is not in this fleet's scope: no Meshy, no Blender, no Unity, no rigs. Hand 3D work to Games.
